# Borrower 最小可运行流程

目标：文字找衣服 → 选择商品 → 明确确认预约 → 立即占用 → 重启不丢。

面向 Hackathon，沿用 `BACKEND_SPEC.md` 的数据和日期规则，只实现 borrower。按以下三个阶段连续推进，每阶段先跑通再进入下一阶段，不需要逐阶段等待确认。

## 阶段 1：搜索和预约，不接 LLM

- 加载 catalog，建立内存存储和日期、尺码、城市校验。
- 实现搜索和预约入口，用结构化请求即可调用；搜索使用确定性排序。
- 预约时在锁内重新检查，同步更新预约数据，写入 JSON 快照。
- 使用 `Garment`、`Booking`、`SearchRequest`、`Feasibility`、`SearchHit`。

验收：固定演示日期，输入 Hamburg、EU 38 和穿着日期能找到可借商品；预约后同日期搜索不再出现该商品；并发预约只能成功一次；重启后预约仍在。运行日期计算和预约冲突的针对性测试。

## 阶段 2：接上 borrower 对话

- 增加 `BorrowerState`，从文字提取日期、城市、尺码及可选偏好。
- 缺少必要信息时追问，不猜测；调用阶段 1 的搜索并解释结果。
- 只在明确选择商品并确认预约后调用预约能力；日期和可用性始终由代码判断。
- 本阶段可通过 API 客户端验证，不依赖页面。

验收：完成“我周五要参加晚宴”→ 补充城市和尺码 → 返回推荐 → 明确预约某件商品；未确认时不创建预约，无结果或调用失败时给出可继续操作的提示。

## 阶段 3：最小页面和完整演示

- 接入聊天输入框、商品卡片、预约按钮，以及成功、冲突和错误提示。
- 预约按钮明确表示确认预约；展示结果以实际后端返回为准。
- 用真实后端完成浏览器联调，保留一条固定日期的演示路径。

验收：浏览器走完搜索到预约；两个窗口预约同一件商品的重叠日期，只有一个成功，另一个显示冲突；刷新或重启后已预约商品仍不可借。

## 暂不实现

lender、上架、图片上传与识别、搭配推荐、MCP、LLM 二次排序、复杂条件放宽，以及数据库或多进程部署。保留单进程、内存字典和 JSON 快照。

执行原则：可以在一个任务中连续完成三个阶段，但不要等全部写完才第一次运行；本计划未包含的完整规范功能不作为本轮验收要求。
