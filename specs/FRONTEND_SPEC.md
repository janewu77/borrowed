# MORE — Frontend Implementation Spec

**Version 1.0 · 12 September 2026 · derived from `ARCHITECTURE.md` + `SPEC.md`**
**Audience: an AI coding agent. Pairs with `specs/BACKEND_SPEC.md`.**

---

## 0. Rules of engagement (not negotiable)

1. **The server owns slot state.** The browser holds only `conversation_id` and the
   message list. There is no second state machine, no client-side slot filling.
2. **No date arithmetic in the frontend — not even for display.** `ship_by`,
   `lands_on`, `free_again` arrive as ISO strings and are only *formatted*
   (`Thu 17 Sep`). Never `+ 1 day`, never a duration computed in JS. Add an ESLint
   rule banning `date-fns/add*`, `setDate`, and arithmetic on `Date` objects.
3. **No model calls from the browser.** No API keys in client code, ever.
4. **The borrower's reference photo is never persisted or cached** — not in
   `localStorage`, not in a state store, not in a service worker. It is attached to
   one multipart turn and dropped.
5. Vocabulary is **borrower / lender**. `renter` and `owner` appear nowhere in
   components, routes, copy or types.
6. Next.js 15 App Router, TypeScript strict, Tailwind. Server Components by default;
   one Client Component subtree for the conversation.

## 1. Routes

| Route | Rendering | Purpose |
|---|---|---|
| `/` | static Server Component | choose a side — two large buttons, `I need something to wear` → `/find`, `I have something to lend` → `/list` |
| `/find` | Client subtree | borrower conversation |
| `/list` | Client subtree | lender conversation |
| `/garment/[id]` | Server Component | **original photo first**, gallery, availability timeline, lender, price |
| `/lender/[lenderId]` | Server Component | the lender's garments with incoming holds and each `ship by` line |

`/garment/[id]` fetches `GET /api/garments/{id}` server-side. When the URL carries
`?wear=YYYY-MM-DD` it also fetches `/availability` and renders the timeline for that
window; without it the timeline shows existing holds only.

## 2. Types — generated, not hand-written

Generate `lib/api-types.ts` from the backend's Pydantic models
(`datamodel-code-generator` → OpenAPI → `openapi-typescript`, or an export script).
Committed, regenerated by `npm run gen:types`. **Hand-editing this file is a bug.**

The SSE union must come from the same generation step:

```ts
type SseEvent =
  | { event: "token";         data: { text: string } }
  | { event: "question";      data: { text: string; fields: string[] } }
  | { event: "listing_draft"; data: { draft: ListingDraft } }
  | { event: "results";       data: { hits: SearchHit[]; relaxed: string | null } }
  | { event: "availability";  data: { feasibility: Feasibility; garment: GarmentPublic } }
  | { event: "booking_claim"; data: { booking: BookingResult } }
  | { event: "error";         data: { message: string; recoverable: boolean } }
  | { event: "done";          data: { conversation_id: string } };
```

## 3. Components

### 3.1 `ChatStream` (client) — the only place that touches the stream

- Owns: `messages: ChatItem[]`, `status: "idle" | "streaming" | "error"`, `conversationId`.
- `POST /api/conversations/{id}/turn` as `multipart/form-data` (`text`, optional `image`),
  read with `fetch` + `ReadableStream` (**not** `EventSource` — it cannot POST).
- Dispatches each `SseEvent` to a reducer that appends a typed `ChatItem`.
  `token` events append to the **last assistant bubble**; every other event pushes its
  own card. Unknown event names are ignored, never thrown.
- On `error` with `recoverable: true`, show an inline retry affordance and keep the
  conversation; on `false`, end the turn with a plain message.
- Abort the in-flight `fetch` on unmount and on a new turn.

### 3.2 `AgentQuestion` — the component that must be visibly different

Renders a `question` event. **It must not look like an answer.** Left accent bar,
tinted background, a `still needed` label, and the `fields` rendered as chips
(`wear date`, `size`). A quick-reply row: date chips for the next 14 days when
`wear_date` is missing, EU-size chips 34–44 when `sizes_eu` is missing — tapping one
sends the turn immediately.

This is SPEC §1.2's defining behaviour. A judge has to *see* the product ask instead
of guess, so this component gets real design attention.

### 3.3 `ResultCard` — three per answer

Layout, top to bottom: image (4:5, `next/image`, `thumb` with `image` fallback) ·
name + designer · lender name and rating · `€{rental_price} · {rental_days} days` ·
**a delivery line `lands Thu 17 Sep`** in a high-contrast pill · one-line reason from
the composer · `View` → `/garment/{id}?wear={wear_date}` · `Reserve` (borrower only).

The `lands` pill is the product's thesis on the card. It is never optional and never
computed client-side — it is `feasibility.lands_on`, formatted.

### 3.4 `AvailabilityTimeline` — four bars, and the fourth is the point

Bars: **ship** (`ship_by → lands_on`) · **wear** (`wear_from → wear_to`) ·
**return** (`wear_to → back_by`) · **cleaning** (`back_by → free_again`).

- The cleaning bar is labelled **`cleaning`**. Never `booked`, never `unavailable`.
- A caption states the ratio in words from the dates given:
  `held 16–24 Sep · worn 18–21 Sep`.
- Existing holds on `/garment/[id]` render as muted bars on the same axis.
- Horizontal scroll container at narrow widths; the axis never forces page scroll.

### 3.5 `ListingDraftCard` (lender)

Every field row carries a provenance badge from `draft.provenance[field]`:
`from photo` (outline) or `you said` (filled). When `size_unverified` is true a
`size not verified` warning sits on the size row. A `Publish` button is enabled only
when the backend marks the draft ready. After publish, show `ship by {ship_by_hint}`
on the resulting garment card.

### 3.6 `PhotoInput` — two modes, and they behave differently

| mode | used on | behaviour |
|---|---|---|
| `persist` | `/list` | preview stays, the original is uploaded and stored server-side |
| `ephemeral` | `/find` | preview is a `URL.createObjectURL` revoked on send; the file is attached to one turn and dropped; a caption reads **`used to understand your style, not saved`** |

In `ephemeral` mode: no `localStorage`, no IndexedDB, no state-store retention, and
`URL.revokeObjectURL` in a cleanup effect. Assert this in a Playwright test.

### 3.7 `BookingConfirm`

Reserving is a two-step: `Reserve` opens a confirm sheet showing garment, dates,
`ship by`, `lands on`, price, and the line **`reserved · no payment taken`**. Only
the sheet's confirm button sends the booking turn, with a client-generated
`idempotency_key` (uuid v4, regenerated per sheet-open, reused across retries) and
the button disabled while in flight.

On `booking_claim`, render a success card repeating `reserved · no payment taken`.
On a 409, render the returned `reason` through the same copy map as `ResultCard`.

## 4. Reason copy map (`lib/reasons.ts`)

The only place an enum becomes English in the frontend. Used for badges and empty
states; the agent's own streamed sentences are separate.

| enum | copy |
|---|---|
| `TOO_LATE_TO_SHIP` | can't arrive in time |
| `OUTSIDE_LENDER_WINDOW` | outside the lender's dates |
| `OVERLAPS_BOOKING` | already booked for those days |
| `IN_CLEANING` | still in cleaning |
| `SIZE_MISMATCH` | not in your size |
| `WRONG_CITY` | not in Hamburg |

Unknown enum value → render nothing rather than the raw string.

## 5. Date formatting (`lib/dates.ts`)

One module, ~10 lines, the **only** file allowed to import a date library:

```ts
export function fmtDay(iso: string): string   // "2026-09-17" -> "Thu 17 Sep"
export function fmtRange(a: string, b: string): string  // "16–24 Sep"
```

Locale `de-DE` with English month abbreviations (`en-GB` formatting, Europe/Berlin
timezone). Parse-and-format only — **no arithmetic, no `Date` math, no timezone
shifting**. Never construct a `Date` from a bare `YYYY-MM-DD` without forcing UTC,
or the 17th renders as the 16th for some viewers.

## 6. Two-window demo requirements

The strongest demo moment (ARCHITECTURE §7): book in one window, watch the dress
disappear from the other's results.

- `/find` re-runs its last search when the tab regains focus (`visibilitychange`),
  so the second window updates without a manual reload.
- `ResultCard` keys are `garment_id`, so a removed garment animates out rather than
  a whole list re-mount.
- A garment that vanished between search and reserve shows the 409 reason inline
  rather than an error toast.

Do not add WebSockets for this. Focus-refetch is enough and cannot break the stream.

## 7. Loading, empty and error states (all three are demo-visible)

| state | treatment |
|---|---|
| ranking in flight | a `looking through 386 garments…` line, not a spinner — it names what is happening |
| vision call (5–10s, lender) | streamed progress line; the publish button is never blocked by normalisation |
| 0 feasible results | the agent's explanation plus up to 5 near-miss cards, each with its reason badge and `AvailabilityTimeline` — **never an empty screen** |
| relaxed search | a `relaxed: {axis}` chip above results, e.g. `also showing: other occasions` |
| stream dies | inline retry that re-sends the same turn; the conversation is not lost |

## 8. Styling

Tailwind, no component library. One palette in `tailwind.config.ts`; feasible/
infeasible are the only semantic colours (`ok` and `muted` — not red/green: nothing
here is an error, a refusal is an honest answer). System font stack. Respect
`prefers-color-scheme`; define the light palette on `:root` and override tokens in
the dark block — never define a colour only inside a media query.

Responsive down to 400px: result cards stack to one column, the timeline gets its own
`overflow-x:auto` container, the composer stays pinned to the bottom.

Accessibility: `AgentQuestion` is `role="status"` `aria-live="polite"`; every image
has alt text from `name`; quick-reply chips are real `<button>`s; focus never leaves
the composer after a turn.

## 10. Definition of done

- [ ] `/find`: a turn with no date and no size produces a visibly distinct
      `AgentQuestion` with quick-reply chips — **no search is issued**
- [ ] A complete turn renders three `ResultCard`s, each with a `lands …` pill
- [ ] `AvailabilityTimeline` shows four bars and the fourth says `cleaning`
- [ ] Reserve → confirm sheet → `reserved · no payment taken` success card
- [ ] Two windows side by side: booking in one removes the garment from the other on focus
- [ ] A borrower photo leaves no trace — verified by a test asserting empty
      `localStorage`/IndexedDB and a revoked object URL
- [ ] `grep -r "renter\|owner" frontend/` returns nothing
- [ ] No date arithmetic in the bundle: `lib/dates.ts` is the only date-library importer
- [ ] 400px viewport: no horizontal page scroll on any route
